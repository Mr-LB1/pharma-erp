# 医药 B2B ERP · 从 0 到 1 实现方案（Vibe Coding 施工蓝图）

> 定位：面向药企/医药流通企业的采购、销售、仓储、库存、供应商与客户管理场景。
> 技术栈：**Spring Boot + Vue 3 + PostgreSQL**（已确认）。MVP 目标：**真实可用**（多用户 + 权限 + 审批真跑通）。
> 本文档是后续用 AI 辅助编码（vibe coding）时的**唯一事实来源（Single Source of Truth）**——数据模型、接口契约、业务规则都先冻结在这里，再让 AI 生成代码。

---

## 0. 三个必须先拍板的技术前提

### ⚠️ 前提一：升级 JDK（当前是硬阻塞）

你机器现在是 **Java 8（`F:\jdk_1.8`）**，但：

| 事实 | 影响 |
|---|---|
| Spring Boot 2.7 已于 2023-11 停止维护（EOL） | 医药系统**不能**用无安全补丁的框架 |
| Spring Boot 3.x 强制要求 **JDK 17+** | 必须升级 JDK 才能用现代版 |

**结论：装 JDK 17（或 21，均为 LTS），后端用 Spring Boot 3.3.x。** 这是开工前第一件事，我可以帮你下载配置（阿里云镜像/代理）。

### 前提二：数据库迁移用 Flyway，不用 `ddl-auto=update`

开发期 `ddl-auto=update` 方便，但真实 MVP 要**表结构版本化**：每次改表 = 一个可 review 的迁移脚本（`V1__init.sql`、`V2__add_xxx.sql`…）。这样 AI 改表结构你也能一眼看出它动了什么，且可回滚、可审计。

### 前提三：核心业务规则必须先写测试，再让 AI 实现

FEFO 选批、效期阻断、追溯完整性、移动加权成本——这些是 **GSP 红线**，人肉验证不可靠。**每个规则先写一条自动化测试用例（描述期望），再让 AI 实现直到测试通过。**

## 1. 系统架构（单体优先）

```
浏览器 (Vue3 + Element Plus)
        │  HTTPS / JWT
        ▼
   ┌─────────────────────────────┐
   │        Spring Boot 3.x       │
   │  Controller  (REST /api)     │
   │  Service     (业务规则/事务)  │
   │  Repository  (Spring Data JPA)│
   │  Security    (JWT + RBAC)    │
   │  Approval    (审批流)         │
   └──────────────┬──────────────┘
                  │ JDBC (Flyway 迁移)
                  ▼
          PostgreSQL 17 (vue_demo 库 / 生产独立库)
```

- **单体模块化（modular monolith）**：按业务域分包，暂不拆微服务——MVP 拆微服务是过度设计。
- **单租户**：一个企业实例一套数据，多租户留到 P3 再议。
- **无状态后端**：JWT 鉴权，便于横向扩展。

## 3. 数据模型（核心表与字段关系）

> 完整 DDL 在编码阶段用 Flyway 生成，这里只冻结**关键字段与关系**——这些是 AI 最容易搞错的点。

### 3.1 权限（RBAC）

- `sys_user`：id, username, password(BCrypt), real_name, dept, status
- `sys_role`：id, code, name
- `sys_permission`：id, code(如 `purchase:order:create`), name, type(菜单/按钮/接口)
- `sys_user_role`、`sys_role_permission`

### 3.2 主数据

**`product`（商品/药品）**：
`id, code, generic_name(通用名), trade_name(商品名), approval_no(批准文号), dosage_form(剂型), spec(规格), manufacturer(生产厂家), rx_category(处方/OTC/特殊管理), storage_cond(常温/阴凉/冷藏), first_audit_status(首营), status`

**`supplier`（供应商）**：`id, name, credit_code, license_no, license_expire, gsp_cert, first_audit_status, settle_type`
**`customer`（客户）**：`id, name, license_no, license_expire, credit_level, credit_limit, first_audit_status`
**`warehouse` / `location`**：`id, name, temp_type(温控), status`

### 3.3 交易单据（含批号效期，医药核心）

**`purchase_receive_item`（采购入库明细）** —— 追溯的起点：
`id, receive_id, product_id, quantity, batch_no(批号), produce_date(生产日期), expire_date(有效期至), unit_cost(批次采购价), inspection_no(检验报告单号)`

**`sales_delivery_item`（销售出库明细）** —— 必须锁批号：
`id, delivery_id, product_id, batch_no, quantity, unit_cost(结转成本)`

### 3.4 库存 / 追溯 / 成本（灵魂三张表）

**`stock`（批次库存，唯一键 = product_id + batch_no + location_id）**：
`id, product_id, batch_no, produce_date, expire_date, location_id, quantity, unit_cost`

**`stock_transaction`（库存流水，只追加 append-only）**：
`id, product_id, batch_no, op_type(入库/出库/调拨/盘点/报废), ref_type, ref_id, quantity(+/-), before_qty, after_qty, op_user, op_time`

**`lot_trace`（批次追溯，只追加）**：
`id, product_id, batch_no, source_type, source_id, target_type, target_id, quantity, op_time, op_user`

**`cost_ledger`（成本台账，只追加）**：
`id, product_id, batch_no, op_type, quantity, unit_cost, amount(+/-), balance_qty, balance_amount`

> 为什么"流水 + 追溯 + 成本台账"三张都设计成**只追加（append-only）**？——因为 GSP 要求记录不可篡改。追溯不靠查库存快照，而是靠流水回放。

### 3.5 审批 / 审计

- `approval_config`：业务类型, 触发条件(金额阈值/类型), 审批层级
- `approval_record`：业务单号, 节点, 审批人, 状态, 意见, 时间
- `audit_log`：用户, 操作, 对象, 变更前后值, 时间, IP

### 字段关系（ER 简图）

```
supplier ──< purchase_order >── purchase_order_item >── product
                │
                ▼
        purchase_receive_item ──(批号/效期/检验单)──> stock ──> stock_transaction
                                                       │              └──> lot_trace
customer ──< sales_order >── sales_order_item >── product        └──> cost_ledger
                │
                ▼
        sales_delivery_item ──(锁批号)──> stock(扣减)
```

## 4. 核心业务规则（AI 必须实现的"红线"）

| # | 规则 | 说明 | 是否写测试 |
|---|---|---|---|
| R1 | **FEFO 选批** | 出库默认先出"有效期最近"的批次 | ✅ 必测 |
| R2 | **效期阻断** | 过期/近失效批不可销售出库（阈值按品种配置） | ✅ 必测 |
| R3 | **首营阻断** | 供应商/商品/客户未过首营 → 系统层禁止开单 | ✅ 必测 |
| R4 | **证照效期预警** | 许可证到期前 N 天预警，到期锁交易 | ✅ 必测 |
| R5 | **库存不可为负** | 出库数量 > 可用批次库存 → 拒绝 | ✅ 必测 |
| R6 | **移动加权成本** | 入库后 `新单价=(结存金额+入库金额)/(结存数量+入库数量)`；出库按当前单价结转 | ✅ 必测 |
| R7 | **追溯完整性** | 任意批次正向追到客户、逆向追到供应商 | ✅ 必测 |
| R8 | **不可物理删除** | 单据/流水只"作废(红冲)"，不留删记录 | 代码规约 |

## 6. 权限与审批机制

- **RBAC**：角色 → 权限码（`模块:对象:动作`），前端路由守卫 + 后端 `@PreAuthorize` 双重校验。
- **数据权限**：销售员只看自己的单据；成本/价格字段按角色脱敏。
- **审批流**：可配置的"金额分级审批 + 首营强制审批"。状态机：`草稿 → 待审 → 已审/驳回`。
- **审批落库**：每步留 `approval_record`，与审计日志打通。

## 8. 合规与数据安全

- **追溯**：正/逆向全链路，基于 `lot_trace` 流水。
- **首营**：证照过期自动预警 + 锁交易。
- **记录保存**：单据不可物理删除，只红冲留痕；流水表 append-only。
- **审计**：关键操作（改库存/价格/权限、审核、导出）留痕含前后值。
- **传输**：HTTPS；密码 BCrypt；敏感字段（成本）按角色脱敏。
- **备份**：PG 定期备份 + 至少每日。

## 9. 分阶段开发计划（真实可用 MVP 拆分）

### 里程碑 M1 —— 地基（1 周量级）
- 装 JDK17 → 初始化 Spring Boot 3.3 + Vue3 + PG + Flyway
- JWT 登录 + RBAC + 基础资料（商品/供应商/客户/仓库）
- **验收**：能登录、不同角色看到不同菜单、商品 CRUD 落库（Flyway 建表）

### 里程碑 M2 —— 核心交易（2 周量级）
- 采购订单 → 采购入库（批号+效期+检验单号）
- 销售订单 → 销售出库（FEFO 锁批 + 效期阻断 + 库存不可为负）
- 批次库存 + 移动加权成本 + `stock_transaction`/`lot_trace`/`cost_ledger`
- **验收**：完整采购入库→销售出库跑通，库存精确到批次，R1/R2/R5/R6 测试全绿

### 里程碑 M3 —— 合规闭环（2 周量级）
- 首营审核 + 证照效期预警 + 近效期/过期隔离 + 不合格品
- 盘点 + 审批流 + 审计日志 + 基础报表（进销存/近效期清单）
- **验收**：R3/R4/R7/R8 测试全绿，任意批次 1 分钟内完成双向追溯

### 后续 P2/P3（MVP 之外）
- 财务结算/发票、WMS/追溯平台/冷链 IoT 集成、多租户

## 10. Vibe Coding 工作流（关键方法论）

**你的角色 = 领域审查员，AI = 代码工人。** 别让 AI 拍板业务规则，它没有 GSP 知识。

1. **先冻结契约，再生成代码**：每个迭代开始，先写清楚"这个功能的数据表、接口、业务规则、验收点"，再让 AI 生成。
2. **按垂直切片迭代**，不要按横向分层：
   - ✅ 好："实现商品档案的列表+搜索+新增+编辑，含首营状态列"
   - ❌ 差："把所有的 Entity 先都写出来"
3. **红规则先写测试**：FEFO/效期/追溯 用测试用例表达期望，AI 实现到测试通过为止。
4. **每迭代必做四件事**：AI 生成 → **你审业务逻辑** → 跑测试 + 手动点一遍 → Flyway 迁移脚本进 Git。
5. **提交粒度**：一个功能一个 commit，别让 AI 一次吐一大堆改动，否则没法 review。

## 11. 风险与决策记录（ADR）

| 决策 | 选择 | 理由 |
|---|---|---|
| 架构 | 单体模块化 | MVP 不拆微服务 |
| 迁移 | Flyway | 表结构版本化、可 review |
| 鉴权 | JWT + Spring Security | 无状态、B 端通用 |
| ORM | Spring Data JPA | CRUD 快；复杂查询用 JPQL/原生 SQL 兜底 |
| UI | Element Plus | 中文 B 端表格/表单生态最成熟 |
| 成本法 | 移动加权平均（商品级） + 批次级 unit_cost 记录 | 总账价值准 + 批次毛利可分析 |
