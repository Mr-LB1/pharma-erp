# 医药 B2B ERP · 测试用例

> 依据：`../../docs/design/设计方案.md`（§4 业务规则 R1-R8、§9 里程碑）与 `../../docs/collab/协作流程与任务拆解.md`（§三 M1 API 契约，冻结版）。
> 统一响应约定：成功 `{"code":200,"message":"success","data":...}`；失败 `{"code":<非200>,"message":"<原因>","data":null}`。字段命名 camelCase。

## 一、红线规则用例（R1-R8）

### R1 · FEFO 选批（先出有效期最近的批次）— P0 · 设计先行（M2 实现）

| 项 | 内容 |
|---|---|
| 规则描述 | 销售出库默认按"有效期至（expireDate）最早"的批次顺序锁定，先出临近效期批次 |
| 前置条件 | 商品 P 存在 3 个批次库存（同一库位）：批次 A 效期 2026-12-31、批次 B 效期 2027-06-30、批次 C 效期 2026-08-31（均未过期）；各批次库存充足 |
| 测试步骤 | 1. 创建销售出库单，选择商品 P，出库数量 = 1（小于任一批次库存）；2. 触发 FEFO 批次选择/锁批；3. 查看出库明细的批号分配顺序 |
| 期望结果 | 系统默认锁定**批次 C**（效期最早）；出库明细批号按 C → A → B 的 FEFO 顺序自动填充；无人工干预时不得跳过 C |
| 优先级 | P0 |
| 状态 | 设计先行（M2） |

补充场景：

| 场景 | 期望 |
|---|---|
| 两批次效期相同 | 按入库先后（先进先出）或批次号字典序稳定排序，结果确定且可复现 |
| 出库量跨越多个批次 | 按 FEFO 顺序拆分为多行出库明细，数量之和 = 出库总量 |
| 批次选择器展示 | 前端批次选择器按 FEFO 排序，效期临近批次红色/黄色高亮 |

### R2 · 效期阻断（过期/近失效批不可销售出库）— P0 · 设计先行（M2 实现）

| 项 | 内容 |
|---|---|
| 规则描述 | 过期批次与"近失效阈值内"批次禁止销售出库（阈值按品种 storage_cond 或品种配置） |
| 前置条件 | 商品 P 有批次 X（expireDate 已 < 今天）与批次 Y（expireDate 在近效期阈值 N 天内） |
| 测试步骤 | 1. 对批次 X 发起销售出库；2. 对批次 Y 发起销售出库；3. 观察系统响应 |
| 期望结果 | 两次均被系统拒绝：返回非 200 错误码，message 提示"批号 X 已过期，禁止销售出库"/"批号 Y 近效期（剩余 N 天），禁止销售出库"；库存不被扣减 |
| 优先级 | P0 |
| 状态 | 设计先行（M2） |

补充场景：

| 场景 | 期望 |
|---|---|
| 近效期阈值边界（= N 天） | 按"≤ N 天即阻断"的配置口径执行，边界值行为与配置一致 |
| 效期录入非法（expireDate ≤ produceDate） | 入库时即校验拒绝，不允许写入 |

### R3 · 首营阻断（未过首营禁止开单）— P0 · 设计先行（M3 实现）

| 项 | 内容 |
|---|---|
| 规则描述 | 供应商 / 商品 / 客户任一 `firstAuditStatus != APPROVED` 时，系统层禁止相关开单 |
| 前置条件 | 供应商 S 首营状态为 PENDING；商品 P 首营状态为 REJECTED；客户 C 首营状态为 APPROVED |
| 测试步骤 | 1. 为供应商 S 创建采购订单；2. 为商品 P 创建销售订单；3. 为已过首营的客户 C 创建销售订单 |
| 期望结果 | 步骤 1、2 被系统拒绝并提示"供应商/商品未通过首营审核"；步骤 3 正常开单（对照组） |
| 优先级 | P0 |
| 状态 | 设计先行（M3） |

补充场景：

| 场景 | 期望 |
|---|---|
| 首营状态变更后 | APPROVED 后立即可开单，无需重建单据 |
| 越权绕过 | 直接构造 API 请求（绕过前端）仍被后端 `@PreAuthorize`/业务校验拦截 |

### R4 · 证照效期预警（到期前 N 天预警，到期锁交易）— P1 · 设计先行（M3 实现）

| 项 | 内容 |
|---|---|
| 规则描述 | 供应商/客户许可证（licenseExpire）到期前 N 天进入预警列表；到期后锁定该主体交易 |
| 前置条件 | 供应商 S1 licenseExpire = 今天 + N-1 天；供应商 S2 licenseExpire = 今天 - 1 天（已过期） |
| 测试步骤 | 1. 查询证照预警列表；2. 为已过期供应商 S2 开采购订单 |
| 期望结果 | 步骤 1 预警列表包含 S1（含剩余天数），不含已过期 S2 之外的正常主体；步骤 2 开单被锁，提示"供应商证照已过期，禁止交易" |
| 优先级 | P1 |
| 状态 | 设计先行（M3） |

### R5 · 库存不可为负 — P0 · 设计先行（M2 实现）

| 项 | 内容 |
|---|---|
| 规则描述 | 出库数量 > 可用批次库存时系统拒绝，库存量不允许为负 |
| 前置条件 | 商品 P 批次 X 可用库存 10 |
| 测试步骤 | 1. 创建销售出库，出库数量 12（> 10）；2. 并发场景：两个出库单同时各出 6（合计 12 > 10） |
| 期望结果 | 步骤 1 被拒绝并提示"库存不足"；步骤 2 至少一单被拒绝，最终库存不为负（需行级锁/乐观锁保证） |
| 优先级 | P0 |
| 状态 | 设计先行（M2） |

### R6 · 移动加权成本 — P0 · 设计先行（M2 实现）

| 项 | 内容 |
|---|---|
| 规则描述 | 入库后 `新单价 = (结存金额 + 入库金额) / (结存数量 + 入库数量)`；出库按当前加权单价结转成本 |
| 前置条件 | 商品 P 期初库存 100 件，单位成本 10 元（结存金额 1000 元） |
| 测试步骤 | 1. 采购入库 50 件，单价 12 元；2. 查成本：新单价应为 (1000+600)/(100+50)=10.6667；3. 销售出库 30 件；4. 查 cost_ledger 结转金额 |
| 期望结果 | 入库后加权单价 = 10.6667（约 10.67）；出库 30 件结转成本 = 320.00（30×10.6667）；结存数量 120、结存金额 1280.00 |
| 优先级 | P0 |
| 状态 | 设计先行（M2） |

补充场景：

| 场景 | 期望 |
|---|---|
| 多次入库 | 每次入库后单价按最新加权重算，台账逐笔 append 可回放 |
| 出库成本取数 | 出库结转单价 = 出库前当前加权单价，出库不改变剩余单价 |

### R7 · 追溯完整性（正向到客户、逆向到供应商）— P0 · 设计先行（M2-M3 实现）

| 项 | 内容 |
|---|---|
| 规则描述 | 任意批次可正向追溯到客户、逆向追溯到供应商，链路完整基于 lot_trace 流水 |
| 前置条件 | 批次 B：从供应商 S 采购入库 → 销售出库给客户 C（正常业务链路已完成） |
| 测试步骤 | 1. 正向追溯 `GET /api/trace/forward?batchNo=B`；2. 逆向追溯 `GET /api/trace/backward?batchNo=B` |
| 期望结果 | 正向返回下游链路（含客户 C、出库单号、数量）；逆向返回上游链路（含供应商 S、入库单号、数量）；两端链路能拼合为完整批次生命周期 |
| 优先级 | P0 |
| 状态 | 设计先行（M2-M3） |

补充场景：

| 场景 | 期望 |
|---|---|
| 调拨/报废中间环节 | 追溯链路包含调拨、报废等中间节点，不中断 |
| 追溯查询响应时间 | 任意批次 1 分钟内完成双向追溯（M3 验收标准） |

### R8 · 不可物理删除（只红冲/作废，不留删除记录）— P1 · 设计先行（M3 实现，代码规约）

| 项 | 内容 |
|---|---|
| 规则描述 | 单据/流水只"作废(红冲)"，不提供物理删除；流水表 append-only |
| 前置条件 | 存在一张已保存的采购订单/销售单据及对应 stock_transaction/lot_trace/cost_ledger 流水 |
| 测试步骤 | 1. 检查后端是否存在 DELETE 接口（契约层面不应有）；2. 对单据执行"作废"操作；3. 查询数据库记录 |
| 期望结果 | 契约中无物理删除端点；作废后原记录 status 置为 VOID 且保留，同时生成红冲记录（负向流水）；stock_transaction/lot_trace/cost_ledger 无 DELETE 语句 |
| 优先级 | P1 |
| 状态 | 设计先行（M3，代码规约） |

## 二、M1 接口验收用例

> 统一前置：后端已启动（JDK17），Flyway 迁移完成，数据库 `pharma_erp` 可连。

### 2.1 认证（auth）

| 用例编号 | 用例名 | 前置条件 | 测试步骤 | 期望结果 | 优先级 |
|---|---|---|---|---|---|
| AUTH-01 | 登录成功 | 存在合法用户（如 admin/admin123） | `POST /api/auth/login` body `{username, password}` | `code=200`；`data.token` 非空；`data.user` 含 id、username、realName、roles[] | P1 |
| AUTH-02 | 登录失败（密码错误） | 合法用户名 | 用错误密码登录 | `code != 200`（如 401/400）；`data = null`；message 含失败原因 | P1 |
| AUTH-03 | 登录失败（用户不存在） | 无 | 用不存在用户名登录 | `code != 200`；`data = null` | P2 |
| AUTH-04 | 无 token 访问受保护接口 | 不携带 Authorization | `GET /api/products`（无 token） | HTTP 状态码 **401**；body 提示未认证 | P0 |
| AUTH-05 | 带 token 获取当前用户 | 已登录拿到 token | `GET /api/auth/me` 带 Bearer token | `code=200`；data 含 id、username、realName、roles | P1 |
| AUTH-06 | 无效/过期 token | 伪造或过期 token | 带非法 token 访问受保护接口 | HTTP 401 | P1 |
